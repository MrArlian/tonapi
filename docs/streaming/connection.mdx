## Reconnect policy

Both transports use exponential backoff for automatic reconnection on transient failures. Configure via `ReconnectPolicy`:

```python
from pytonapi.streaming import TonapiStreaming
from pytonapi.types import Network, ReconnectPolicy

policy = ReconnectPolicy(
    max_reconnects=10,
    delay=0.5,
    max_delay=10.0,
    backoff_factor=2.0,
)

async with TonapiStreaming(
    "YOUR_API_KEY", Network.MAINNET, reconnect_policy=policy,
) as streaming:
    ...
```

| Parameter        | Default | Description                            |
| ---------------- | ------- | -------------------------------------- |
| `max_reconnects` | 10      | Maximum attempts (-1 for unlimited).   |
| `delay`          | 0.5     | Initial delay in seconds.              |
| `max_delay`      | 10.0    | Upper bound for backoff delay.         |
| `backoff_factor` | 2.0     | Multiplier applied on each attempt.    |

<Warning>
  After an ungraceful disconnect (crash, network drop, killed process) the server may hold the old session open for an extended period. This counts against your connection limit — new connections may fail until the server releases the ghost session. Always use the context manager or call `close_session()` in a `finally` block to close cleanly.
</Warning>

## Reconnect behavior

Errors are split into recoverable and fatal:

| Category    | Errors                                                                                | Behavior                                                                       |
| ----------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Recoverable | `TONAPIServerError` (5xx), `TONAPITooManyRequestsError` (429), `TONAPIStreamingError` | SDK sleeps for the calculated delay and retries the connection automatically.  |
| Fatal       | All other `TONAPIError` subclasses (400, 401, 403, 404)                               | Raises immediately — no reconnect is attempted.                                |

After `max_reconnects` consecutive attempts are exhausted, `TONAPIConnectionLostError` is raised.

### Backoff formula

Each reconnect delay is calculated as:

```
delay = base_delay * (backoff_factor ^ attempt)
```

The result is capped by `max_delay`. With default settings the progression is: 0.5 s, 1.0 s, 2.0 s, 4.0 s, 8.0 s, 10.0 s, 10.0 s, ...

### SSE heartbeat timeout

SSE connections expect a server heartbeat at least every **30 seconds**. If no data arrives within that window, the connection is considered dead and a reconnect is triggered automatically (counted against `max_reconnects`).

## Graceful shutdown

Pass an `asyncio.Event` to any subscription method to stop it without raising:

```python
import asyncio
import signal

from pytonapi.streaming import TonapiStreaming
from pytonapi.types import Network

stop = asyncio.Event()


async def main() -> None:
    loop = asyncio.get_running_loop()
    loop.add_signal_handler(signal.SIGINT, stop.set)
    loop.add_signal_handler(signal.SIGTERM, stop.set)

    async with TonapiStreaming("YOUR_API_KEY", Network.MAINNET) as streaming:
        async for event in streaming.sse.subscribe_transactions(
            accounts=["EQ..."],
            stop=stop,
        ):
            print(event.tx_hash)


if __name__ == "__main__":
    asyncio.run(main())
```

When the event is set, the iterator exits cleanly after the current iteration — no exception is raised.

## Limitations

- **No dynamic subscription.** Once a subscription is started, its parameters (accounts, operations, workchain) cannot be changed. Stop the iterator and start a new one.
- **No connection state callbacks.** There is no way to observe connection state transitions (connecting, reconnecting, etc.) programmatically.
